# What is on disk: the two roots, the manifests, and the `.ink` file

This describes the actual files and directories the scanners in `storage.py` and
`notes.py` read, and what each one means. `entries.md` in this same folder describes
the Python classes a scan turns these into.

## Two separate roots, not two subdirectories of one root

`INKSPIRE_DATA_ROOT` (`inkspire_api/settings.py`'s `data_root`, default
`var/novel-data`) is a git working tree. `storage.Scanner` reads a `stories/`
directory inside it. Every git operation (`GET /api/git/status`,
`POST /api/git/commit`, `/push`, `/pull`, in `inkspire_api/repository.py`) runs
against this working tree.

`INKSPIRE_FILES_ROOT` (`files_root`, default `var/files`) is a second, unrelated
directory: not a git working tree, not committed, created the first time something is
written to it. `notes.NotesScanner` reads it directly — there is no `notes/`
subdirectory inside it the way `stories/` sits inside the data root; the files root
*is* the notes space.

These are two independent trees on disk, not two branches of one tree. Nothing under
`files_root` is ever staged or committed, and nothing under `data_root` is read by
`NotesScanner`.

## The stories root

```
<data_root>/
  stories/
    <one-shot-slug>.ink                       a one-shot: a story with one chapter,
                                               no manifest
    <story-slug>/
      story.yaml                              title, synopsis, chapter order
      chapters/
        <chapter-slug>.ink
        <chapter-slug>.ink
        .gitkeep                              only while chapters/ is otherwise empty
      timeline.yaml                           optional, authored by hand, never
                                               written by this API
      lorebook/
        lorebook.yaml                         optional; presence is what the API
                                               calls "has a lorebook"
        data/...                              authored by hand -- see the `lorebook`
                                               package's own docs for its shape
        build/...                             generated by `lorebook build`, gitignored
        export/...                            generated by `lorebook export`, gitignored
```

A directory under `stories/` is a story **if and only if** it holds a `story.yaml`.
Nothing else about the directory matters — `storage.Scanner._scan()` skips a directory
with no `story.yaml` entirely, the same way it skips a symlink. A loose `.ink` file
sitting directly under `stories/`, with no directory around it, is a one-shot; a loose
file that is *not* `.ink` (a stray `.txt`, for instance) is ignored.

### `story.yaml`

```yaml
title: Example Story
synopsis: |
  One or more paragraphs.
chapters:
  - file: first-chapter.ink
  - file: second-chapter.ink
```

The rule: **the filesystem determines what chapters exist; `story.yaml` determines
the order they are read in.** A chapter entry names a file and nothing else — its
title, status and summary live in the chapter's own header, not here. A file present
in `chapters/` but missing from the `chapters:` list is still a chapter; it is simply
shown after every chapter the list does name (`storage._position_in`). A `git pull`
or a hand-edit that adds a chapter file therefore appears in the tree without anyone
updating this list.

`story.yaml` is the only file this API writes inside a story directory, besides the
chapter files themselves. `timeline.yaml` and everything under `lorebook/` are
authored by hand and only ever read.

### One-shots

A one-shot has no `story.yaml` and no `chapters/` directory — it is a single `.ink`
file, directly under `stories/`, and its own header is the only place anything about
it is recorded. There is no order to set (there is exactly one chapter) and nothing
for a manifest to add. Creating one, renaming one, and deleting one are
`Scanner.create_one_shot()` / `update_one_shot()` / `delete_one_shot()`
(`storage.py`) — each working on the loose file directly, with no manifest ever
touched.

## The `.ink` file, in either root

```
===== ink:meta
title: The Letter in the Study
status: draft
summary: |
  She finally opens it, and it is not what she was told it was.
===== ink:body
She had not opened it. Three years of not opening it, and the wax still held.
===== ink:provenance
"47f57caaa4fb330e": [[18, 45, "gen"], [45, 54, "fix"]]
```

A file is a sequence of named sections, each opened by a fence line and running to the
next fence or to the end of the file. Every section is optional, and **a file with no
fence line anywhere is entirely prose** — which is what a writer gets by creating a
file and typing in it, and which is named after its own filename rather than a `title`.

`ink-format.md` in this same folder is the format in full: the grammar, what each
section means, which rules reading enforces and which `ink check` reports instead, and
why a body is never written without the sections derived from it. `provenance.md`
describes `ink:provenance`, the one section `ink.py` carries without reading.

What matters here, where this document is about what is on disk:

- A key or a section this build does not know is **kept as it is**; a save never
  removes it.
- A broken `meta` section costs the metadata and nothing else — the fences say where
  the prose starts — and a file that cannot be made sense of at all keeps every byte of
  its text as prose. A malformed line never removes a file from the tree.
- `GET .../file/{id}/contents` returns the prose alone. There is no route that writes
  it alone: `PUT .../file/{id}/document` writes the prose and its provenance together,
  keeping whatever header is on disk at the moment of the write — not whatever a client
  last read, so a status or title changed by hand meanwhile is not overwritten.

## The notes root

```
<files_root>/
  scratch.ink                                 a loose note, at the root
  research/
    manifest.yaml                             optional; title and/or context
    worldbuilding.ink
    another-note.ink
```

A directory here is a folder simply by being a directory — unlike a story, it needs
no manifest to exist. `manifest.yaml` is written only when there is something to say
that the directory's own name does not already say: a title the slug cannot spell, or
a context. A folder one level inside another folder is not read at all
(`notes.NotesScanner._folders()` only lists the root's own immediate subdirectories);
one level is the intended depth, a folder being the context a set of notes sharing it
has in common.

### `manifest.yaml`

```yaml
title: Research Notes
context: Background reading for the second draft.
```

Both keys are optional, and the file itself is omitted when neither would be written
(`notes.folder_document()`) — a folder named exactly after its own slug, with nothing
to say about it, has no manifest at all. Note that the YAML key is `context:`, not
`summary:` — this is a naming difference from `story.yaml`'s `synopsis:` that
predates the two sharing one Python field name; see `entries.md`. Both already answer
as `"summary"` in every API response, from before that field was shared as well as
after.

Notes at the root and inside a folder are ordered the same way: alphabetically by
name. This space records no order of its own the way `story.yaml` does, so there is
nothing to set and no `/chapters`-equivalent route.

## Ids

An id is `blake2b(space + "\0" + relpath).hexdigest()[:16]`
(`inkspire_api/fs.py`'s `derive_id`), where `space` is the literal string `"stories"`
or `"notes"` and `relpath` is:

- for a chapter or a one-shot, the path **relative to the git working tree root**,
  including the leading `stories/` (`stories/<slug>/chapters/<file>.ink`, or
  `stories/<slug>.ink` for a one-shot) — this is what lets
  `repository._committable()` recognise a committable path by its literal shape;
- for a note or a notes folder, the path **relative to the files root itself**, with
  no leading `notes/` segment, since the files root has no such segment on disk.

An id is derived, never stored, and never sent as a path by a client — a request
names an id, and the scanner is the only thing that turns it back into a path,
checking `Path.resolve().is_relative_to(root.resolve())` on every resolution and
refusing a symlink that leads outside its own root. Renaming anything changes its
relpath, and therefore its id.

## What git ever sees

Only the data root is a git working tree; only paths under `stories/` inside it can
be committed, and only some of those: `repository._committable()` recognises a
story's own `story.yaml`, a chapter under `<story>/chapters/`, and a one-shot loose at
the `stories/` root. A lorebook, a `timeline.yaml`, and anything under the files root
are never staged by `POST /api/git/commit`, whatever else may have changed alongside
them — see "The notes root" above for why notes are excluded by design, not by oversight.
